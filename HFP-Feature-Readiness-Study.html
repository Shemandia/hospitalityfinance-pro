HospitalityFinance Pro — Feature & Readiness Study

A module-by-module technical audit of the platform, focused on one question: what stands between today's build and books your hotels can actually trust and close. Verified against the live codebase (133k LOC), the two prior inspection reports, and git history — not taken on faith.

This is a serious, well-architected financial ERP — multi-tenant (database-per-tenant with row-level security), multi-entity (Group → Property), multi-currency, with a real SunSystems-style report writer (FAL/FSL/FTL), a working Transfer Desk import subsystem with its own format engine (fsd-engine) and sandboxed transformation language (tml-engine), plus PMS/POS/bank/payroll connectors and USALI hospitality P&L. The double-entry plumbing — row-locking on posting, atomic balance upserts, Decimal money math — is solid where it counts. Many critical issues from the April inspections have genuinely been fixed.

But it cannot yet be trusted to close a month or a year. A small number of deep, cross-cutting defects break the one thing a finance system exists to do — produce a correct trial balance and balance sheet. The gap is not breadth (breadth is excellent); it's a handful of correctness fixes at the core. Fix the nine P0 items and this crosses from "impressive demo running on live data" to "system of record."

The one-sentence diagnosis: the ledger never carries balances forward from one period to the next, the reporting materialized view never gets created (a table-name casing bug), and the system posts and pays net of tax — so trial balance, balance sheet, KPIs, and Tanzanian VAT are all wrong today, even though every screen and module exists and looks finished.

What's working (and worth protecting)

The strengths are real and should not be disturbed while fixing the rest. These are the load-bearing walls.

Core ledger discipline

  • Double-entry is enforced in functional currency and re-checked at period close (gl/service.ts:218).
  • Row-locking on posting (SELECT … FOR UPDATE) across AP, AR, receipts, payment runs and periods — no double-posting races.
  • Atomic balance updates via INSERT … ON CONFLICT DO UPDATE with SQL-side Decimal addition — no lost updates under load.
  • Decimal money math throughout the core GL/AP/AR paths — no float drift where it matters.

Platform & security

  • Database-per-tenant + row-level security for entity isolation. The April "RLS disable" and hardcoded-platform-key criticals are verified fixed (migration 20260413…_fix_rls_bypass).
  • Real RBAC with a privilege ceiling and entity-lineage scoping; startup fails if secrets are unset.
  • Advisory-lock process locks serialize period-close / consolidation / depreciation against double-runs.
  • Fail-closed transformation sandbox (refuses insecure VM in production).

SunSystems-class capability

  • Genuine Q&A-style report writer — FAL (account listing), FSL (P&L/BS/CF), FTL (transaction listing) with drill-down and seeded USALI departmental P&L (reporting/report-engine.ts).
  • Transfer Desk is end-to-end and governed — upload → detect → parse → transform → held batch → review → commit through GL approval, not a bypass.
  • Own format engine + transformation DSL (fsd-engine, tml-engine) — the actual SunSystems differentiator, and it's real.

Breadth already built

  • All role dashboards are API-wired (CFO, Controller, GM, Night Audit, Cost Controller, Directors) — no mock dashboards.
  • Strong connectors: Mews and the generic Inbound path are reference-quality (transactional, Decimal-clean, suspense-balanced); SAF/.SUN Opera import is solid.
  • Fixed-asset depreciation is idempotent; intercompany dual-posting (new path) updates both entities in one transaction.
  • Periods, allocations, budget, bank reconciliation, fixed-asset lifecycle — all present and functional.

Roadmap to production

A sequence, not a backlog. Each phase leaves the system in a more trustworthy state than the last. Phase 1 is the difference between "wrong numbers" and "right numbers"; everything after is polish, safety, and reach.

Phase 1 · Make the numbers correct P0 · ~2–4 weeks

Goal: a trial balance and balance sheet you can trust; VAT-correct AP/AR; TZS shown and paid correctly.

  • Build the opening-balance / carry-forward engine — next period's opening = this period's closing for balance-sheet accounts; cumulative within-year for P&L. Then re-point year-end cleardown at true annual balances.
  • Fix the materialized-view casing bug (performance.sql + 20260322 migration → snake_case) and make the MV refresh after posting. Unblocks all KPI / balance-sheet / cash-flow 500s.
  • Add a VAT/tax engine: tax-code → GL mapping, post input & output VAT, pay gross in payment runs, VAT-return report.
  • Add a currency-decimal registry (TZS = 0) feeding both on-screen formatting and every payment-file format.
  • Unify the balance-update path to one signed writer; delete the divergent unsigned FX/fixed-asset writers. Fix the FX-revaluation sign bug and idempotency double-post.
  • Fix consolidation: translate eliminations to reporting currency; fail (don't 1:1) when a rate is missing.
  • Aggregate journal lines by account before balance update (kills the duplicate-account post crash).

Phase 2 · Close the workflow gaps P1 · ~3–5 weeks

Goal: a finance clerk can run the full monthly cycle from the UI without SQL.

  • Import idempotency — content-hash / unique-constraint on the generic Transfer Desk path, bank, and Sky Jana so re-runs can't duplicate journals; wrap commits in transactions and make them resumable.
  • Overdue-aging job so dunning actually fires; fix or remove the broken collection-run.
  • Kill remaining float on money in fsd-engine coercion, tml-engine money functions, and the bank / Sky Jana parsers.
  • Wire the already-built endpoints with no UI: report scheduling, AR receipts register, AP/AR invoice edit/delete/void, user activate-deactivate.
  • Segregation of duties: enforce creator ≠ approver; consolidate the two overlapping journal-approval systems into one.
  • Entity-scope + RLS on Transfer Desk batch tables; make background jobs (dunning, recurring, reports) tenant-aware.
  • Client-side numeric validation on money inputs; realized FX gain/loss on settlement; AR credit notes & write-offs.

Phase 3 · Make it safe to operate P2 · ongoing

Goal: you can run it for real customers and sleep at night.

  • Backups / point-in-time recovery per tenant DB; encrypt tenant connection strings at rest.
  • Monitoring & alerting: error tracking (e.g. Sentry), job dead-letter queues, health metrics — today job failures only hit the console.
  • Test suites for the FSD/TML engines and sandbox-security (currently zero), plus regression tests for the P0 fixes.
  • Harden AsyncLocalStorage tenant context (drop enterWith for runWithContext); add entity_id + RLS to child line tables; default-deny auth.
  • Add multi-dimensional analysis-code masters (validate dimension1–6) to reach true SunSystems analysis-ledger depth.
  • Retire dead code: legacy intercompany no-op path, orphan parsers, unused RabbitMQ, duplicate entity stores.

Method. Six parallel domain audits read the live source at file/line granularity — GL core; AP/AR; multi-entity finance (FX, consolidation, intercompany, budget, fixed assets); Transfer Desk & connectors; platform/tenancy/security; web UI & reporting — cross-checked against the two April inspection reports and git history, then reconciled. The two root-cause claims (missing balance carry-forward; materialized-view casing bug) were re-verified by hand in the code. Findings reflect the codebase as of the last commit (12 Jun 2026).
