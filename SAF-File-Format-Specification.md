# SunAccount SAF Transfer File Format Specification

## For FinSys Hospitality — Integration Reference

---

## 1. Overview

The SAF (Standard Accounting File) is a fixed-width text file format defined by Infor SunSystems for importing journal transactions into SunAccount. It is the standard interface used by integrated systems — including **Sky Jana** (materials/purchasing), **SunBusiness**, PMS systems, and POS systems — to post financial transactions into the General Ledger.

FinSys Hospitality supports importing SAF files from any system that outputs this format. This document covers the complete field specification, parsing rules, and integration notes specific to Sky Jana purchasing vouchers.

### Key Characteristics

- Each record is a **fixed-width line** (typically 512 characters, padded with spaces)
- Fields are identified by **character position** (1-based indexing)
- Unused fields must be **space-filled** (not null/empty)
- Debits and credits within a file **must balance to zero**
- The file may begin with a `VERSION` header line and/or a Control Record
- Transaction lines use Record Type `L` (or `M` for extended analysis codes T0–T9)

### File Line Types

| Line Type | Identifier | Required | Purpose |
|-----------|-----------|----------|---------|
| VERSION header | Starts with `VERSION` | No | File format version (e.g. `42001`) |
| Control Record | Record Type = `C` at position 33 | No | Metadata (highest journal number, cleardown sequence) |
| Transaction Line | Record Type = `L` or `M` at position 33 | Yes | One debit or credit posting line |

## 2. Control Record Layout

The Control Record is optional for journal import (JI-Journal Import shows a warning if absent). It occupies positions 1–512.

| Field | Start | Length | Format | Notes |
|-------|-------|--------|--------|-------|
| Filler | 1 | 32 | Spaces | |
| Record Type | 33 | 1 | `C` | Identifies this as a Control Record |
| Highest Journal Number Used | 34 | 7 | Numeric | |
| Last Cleardown Sequence Used | 41 | 5 | Numeric | |
| Filler | 46 | 2 | Spaces | |
| Language Id | 48 | 2 | Alpha | |
| Filler | 50 | 463 | Spaces | Pad to 512 chars |

## 3. Transaction Line Layout

Each transaction line represents **one side** of a journal entry (either a debit or a credit). Lines are grouped into balanced sets where total debits equal total credits.

### Primary Fields (Positions 1–191)

| Field | Start | Length | Format | Description |
|-------|-------|--------|--------|-------------|
| **Account Code** | 1 | 10 | Alphanumeric | GL account or vendor/creditor code. Numeric codes (e.g. `13050`) are expense/asset accounts. Alpha-prefixed codes (e.g. `CFIKI001`) are vendor creditor accounts. |
| Filler | 11 | 5 | Spaces | |
| **Accounting Period** | 16 | 7 | `YYYYPPP` | Fiscal year + period number. Example: `2025006` = FY2025, Period 6 (June). |
| **Transaction Date** | 23 | 8 | `YYYYMMDD` | Date of the transaction. Example: `20250610`. |

| **Journal Number** | 34 | 7 | Numeric | Journal number. Often blank in import files (assigned by the GL system on import). In SunBusiness files, positions 34–35 are SOURCE (2 chars) and 36–40 are Journal Number (5 chars). |

## 4. Account Code Conventions

SAF files use two distinct account code patterns:

### Numeric Accounts (GL Expense/Asset/Revenue)

These are direct General Ledger account codes. In a hospitality context with USALI-aligned charts:

| Code Range | Typical Category | USALI Department |
|-----------|-----------------|-----------------|
| `13xxx` | Cost of Sales — Food & Beverage | Rooms / F&B |
| `23xxx` | Tax Accounts (VAT Input) | Cross-departmental |
| `43xxx` | Cost of Sales — Other (e.g. tobacco, retail) | Other Operated |
| `60xxx` | Undistributed Expenses — Chemicals, Pool | Property Ops |
| `62xxx` | Energy/Fuel Costs | Utilities |
| `67xxx` | Engineering Supplies | Maintenance |
| `68xxx` | Utilities (water, electricity) | Utilities |

### Alpha-Prefixed Accounts (Vendor/Creditor)

Creditor accounts begin with `C` followed by an abbreviated vendor name and a sequential number:

| Pattern | Example | Vendor Name |
|---------|---------|-------------|
| `CBORA001` | `CBORA001` | Bora Utu Water Services |
| `CFIKI001` | `CFIKI001` | Fikirini Mohammed Juma |
| `CFARI001` | `CFARI001` | Farid Supplies |
| `CGRAN001` | `CGRAN001` | Grano Italiano Ltd |
| `CPURC001` | `CPURC001` | Cash Purchases (petty cash) |

## 5. Amount Parsing Rules

The Amount field (position 48, length 18) requires careful handling because different source systems use different conventions:

### Standard SAF Format
Per the SunSystems specification, the amount is stored as **15 integer digits + 3 decimal digits** with no decimal point. Example: `000000000015652170` = 15,652.170.

### Jana/Practical Format
Sky Jana (and potentially other integrated systems) **mixes formats** within the same file:

1. **Amounts without decimal point**: Treated as **whole numbers** (no implied decimals), especially for currencies with 0 decimal places like TZS. Example: `000000000000120000` = 120,000 TZS.

2. **Amounts with explicit decimal point**: Parsed as-is. Example: `000000000015652.17` = 15,652.17 TZS, `000000002340900.02` = 2,340,900.02 TZS.

### Recommended Parsing Logic

```
IF amount_string CONTAINS '.'
    THEN parse as floating-point number directly
ELSE
    THEN parse as integer (whole number, no implied decimals)
```

This is the **only** strategy that produces balanced files for Jana output. The standard SAF 15+3 implied decimal approach does NOT balance Jana files correctly.

### Verification
With the correct parsing, a Jana purchasing file should always balance:

| | TZS Amount |
|---|---|
| Total Debits | 25,007,095.11 |
| Total Credits | 25,007,095.11 |
| **Difference** | **0.00** |

## 6. Analysis Code Mapping

Analysis codes T0–T9 are flexible dimension fields. Their meaning depends on the source system configuration. For Sky Jana purchasing:

### T0 — VAT/Tax Rate

| Value | Meaning | Application |
|-------|---------|-------------|
| `18` | 18% VAT | Standard-rated supplies |
| `0` | 0% / Exempt | Zero-rated or VAT-exempt items |

Used for: VAT calculation and reporting. Maps to `tax_code` in FinSys.

### T1 — Department Code

| Value | Department | USALI Category |
|-------|-----------|---------------|
| `610` | Food & Beverage | Departmental — F&B |
| `210` | Kitchen / Culinary | Departmental — F&B (sub) |
| `800` | Property Operations & Maintenance | Undistributed — POM |

Used for: Departmental cost allocation. Maps to `department_id` in FinSys.

### T5 — VAT Rate Echo
In Jana files, T5 mirrors the T0 value. This appears to be a system-level duplication, not a separate dimension.

### T2–T4, T6–T9
Not used in the sample Jana purchasing file. Available for custom analysis dimensions in other integrations.

## 8. Balanced Entry Structure

A SAF file represents one or more **balanced journal entries**. Within the file:

- **Every debit line has a corresponding credit line** (or set of credit lines)
- The **sum of all debits must equal the sum of all credits**
- Lines are typically grouped by Transaction Reference (PO/invoice number)

### Jana Purchasing Pattern

```
DEBIT  13050  (Cost of Food)        120,000.00  → Expense account
DEBIT  23100  (VAT Input)            18,000.00  → Tax recovery account
CREDIT CGRAN001 (Grano Italiano)    138,000.00  → Vendor creditor account
```

For each purchase voucher processed through Jana:
1. **Debit** the appropriate cost/expense account for the net amount
2. **Debit** the VAT input account for the tax amount (if VAT-rated)
3. **Credit** the vendor creditor account for the gross amount (net + VAT)

## 10. FinSys Import Workflow

### Step 1: Upload & Preview

Upload the SAF file to the preview endpoint. FinSys parses the file, validates the format, and returns a summary without creating any GL entries.

```
POST /api/v1/import/saf/preview
Content-Type: multipart/form-data

file: Jana-IN-Purchasing-11061306.txt
```

Returns: line count, debit/credit totals, balance check, unique accounts, date range, errors.

### Step 2: Account Mapping

Upload the file to the account-mapping endpoint to see which SAF account codes match existing FinSys GL accounts:

```
POST /api/v1/import/saf/account-mapping
```

Returns each SAF code with status: `matched` (exact code match), `partial_match` (similar code), or `unmatched` (needs manual mapping or auto-creation).

### Step 3: Execute Import

```
POST /api/v1/import/saf/execute
Content-Type: multipart/form-data

file: Jana-IN-Purchasing-11061306.txt
propertyId: <uuid>
groupingStrategy: "single_entry"    // or "by_reference", "by_journal_type"
autoPost: false                     // true to auto-post to GL
autoCreateAccounts: true            // create missing accounts automatically
departmentMapping: {"610": "<dept-uuid>", "800": "<dept-uuid>", "210": "<dept-uuid>"}
sourceModule: "PROC"
descriptionPrefix: "Jana Purchasing"
```

### Step 4: Review & Post

If `autoPost` is `false`, review created journal entries in the GL module and post manually after verification.

## 11. Integration Notes

### Sky Jana Configuration
- Jana exports purchasing vouchers in SAF format with journal type `MFMCP`
- File naming convention: `Jana-IN-Purchasing-{DDMMYYHH}.txt`
- Files are typically generated daily or per batch of approved purchase vouchers
- Each file contains vouchers for a single property

### Scheduled Import
For automated daily imports, configure a file watcher or cron job:
1. Jana deposits SAF files to a shared directory or SFTP endpoint
2. FinSys picks up new files, runs preview validation
3. If balanced and all accounts mapped, auto-import and post
4. If errors, queue for manual review with notification to finance team

### Multi-Property Chains
- Each Jana instance typically serves one property
- SAF files should be imported into the correct property context
- Cross-property transfers require separate handling (not via SAF)

### Currency Handling
- The Conversion Code field (position 187) specifies the transaction currency
- For multi-currency environments, ensure exchange rates are loaded for the transaction date
- TZS amounts from Jana are typically whole numbers (0 decimal places)
- USD/EUR amounts may use 2–3 decimal places

## 12. Error Handling

### Common Import Errors

| Error | Cause | Resolution |
|-------|-------|------------|
| File out of balance | Debits ≠ Credits | Check source system; file may be corrupt or incomplete |
| Unknown account code | SAF code not in GL | Map to existing account or enable auto-create |
| Closed fiscal period | Transaction date falls in a closed period | Re-open period or adjust transaction date |
| Header account posting | SAF code maps to a summary/header account | Map to a postable (non-header) sub-account |
| Duplicate import | Same file imported twice | Check import history; system prevents duplicate batch IDs |

### Validation Checklist

Before importing any SAF file, verify:

- [ ] File balance: total debits = total credits
- [ ] All account codes are mapped to FinSys GL accounts
- [ ] Transaction dates fall within an open fiscal period
- [ ] Currency code is valid and exchange rates are available
- [ ] Department mappings are configured for analysis codes
- [ ] Journal type is recognized
